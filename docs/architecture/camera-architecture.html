The verdict is different from dialogue and fade

The shared foundation is being reused, correctly. MapCamera is the same script in both scenes, and both cameras carry the identical three-component stack. UniversalAdditionalCameraData is not a new script at all — URP adds it to every camera automatically.

And the two follow policies genuinely should be separate. The battle camera is welded to a grid cursor that moves in whole tiles and stores its position as a Vector2Int; the hub camera follows a character moving continuously at sub-tile speed. Trying to serve both from one class would mean a policy switch inside every method. This is not the dialogue story repeating.

The duplication is about five lines of viewport arithmetic — worth folding into MapCamera, which already owns those numbers, but not urgent.

The real problem: camera focus is a one-way door

A scripted event can point the camera at another character with the FocusCamera action, which calls cameraRig.Follow(actor.transform). Nothing ever points it back. The only other Follow call in the project is in GurukulBootstrapper, once, when the visit loads.

So an event that focuses on the Guru leaves the camera following the Guru after the event ends — the player then walks off screen with the camera watching someone else. The only way back is for the content author to remember to append a second FocusCamera pointing at the protagonist. That is a rule a person has to keep, not one the system enforces.

The battle map does not have this problem: BeginCinematic and EndCinematic(restoreCenterTile) are a symmetric pair, and handing control back is part of ending.

Not yet live. Neither authored event uses FocusCamera today, so nothing is broken right now. It is a trap set for the first designer who uses the feature.

The fix is small: have GurukulEventRunner remember the target before it changes it and restore it when the sequence ends, the same way it already returns the game state to HubExploration. An explicit FocusPlayer action would be worth adding too, for an event that wants to hand the camera back early.

One smaller thing

GurukulCameraRig reads the viewport once, in Awake, and relies on [DefaultExecutionOrder(100)] to run after MapCamera has added the PixelPerfectCamera. If that read fails it silently keeps its fallback constants — a 480×270 at 32 PPU guess — for the rest of the session, and the room clamp would be computed against the wrong viewport size.

CameraController avoids this by recalculating on its first LateUpdate, with a comment explaining that the pixel-perfect values are not readable until after Awake. The hub rig would be steadier doing the same.
