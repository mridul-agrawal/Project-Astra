The reason given for building a second one is not correct

The header comment on GurukulScreenFade says:

"Its own thing rather than the shared ScreenFader… that one marks itself DontDestroyOnLoad, so a hub-spawned copy would follow the player into the battle map"

That is true of a copy — but the hub never needed to spawn one. SceneLoader instantiates exactly one ScreenFader at boot and it is alive and idle the whole time the hub is running. The obstacle was never lifetime; it was that nothing outside SceneLoader can reach it.

The second reason given — the 0.35s duration — is real, and is a parameter.

What it should be

ScreenFader gains a way to be reached and a way to be awaited:

ScreenFader.Instance · IEnumerator Cover(Action whileBlack, float duration = -1, bool playSound = true)

A doorway calls Cover(swapRoom, 0.2f, playSound: false). SceneLoader keeps calling RunTransition, which becomes a thin wrapper over the same coroutine. GurukulScreenFade and the hub scene's FadeOverlay object both go, and the hub stops carrying a canvas it does not need.

Smaller than the dialogue change by a wide margin: one file deleted, one file gaining two optional arguments.
