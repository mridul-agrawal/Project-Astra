Hub Interaction

Project Astra · what the designer asked for, and what the code does today. Two independent readings — the requirements below are taken from the GDD, not from the code.

Part 1 — Requirements, from the GDD

Source: docs/hub/Gurukul_Hub_Programmer_GDD.docx §4.3 Character Interaction, §4.4 Environmental Object Inspection, §4.5 Contextual Interaction Button, §4.6 Interaction Prompts, §6.4 Objective-Based Interaction Gating, §6.7 Building Entry and Exit.

Reach — when is something interactable

  1. Within one tile of the target's foot position, facing it, with no solid boundary between.
  2. No tile-centre alignment. Visibly adjacent and facing must be enough; the region must tolerate normal sub-tile movement.
  3. Approachable from all four cardinal sides unless the authored placement blocks one.
  4. A large object may supply a wider authored region.
  5. Never through walls, counters, bookcases, house exteriors or the river.

One button, one target

  1. One logical INTERACT covers talk, inspect, enter, leave, report, answer a prompt, and depart.
  2. Discrete: holding must not re-trigger. Re-arms only after release.
  3. Ignored unless the hub is in free exploration.
  4. Exactly one target per press — never every overlapping one.
  5. Priority ladder: open UI or dialogue → character with a conversation → objective-critical object → building entry/exit → other inspectable.
  6. Within a level: most directly in front, then nearest.
  7. Design may supply an explicit override for a deliberately crowded staging.
  8. Mashing while dialogue closes must not reopen it or hit a neighbour.
  9. No valid target = nothing happens. No dialogue, no state change, no progress.
  10. If the target becomes invalid between prompt and press, cancel cleanly and refresh.

The prompt

  1. At most one prompt, only in free exploration, only while in reach and facing.
  2. Lower-centre HUD, sized for 480×270; longer explanation belongs in dialogue.
  3. Shows the bound button glyph plus a verb — Talk, Inspect, Enter, Leave, Report, Depart. Use the specific verb, not a generic one.
  4. Hidden during dialogue, choices, quizzes, events, fades, loading and battle transitions.
  5. Refreshes on facing change, target move, objective change, gate opening, interactable state change, visit change.
  6. Must not flicker at the edge of a region, and must never survive its target being removed.
  7. Changing input device re-glyphs it without changing interaction state.

What a press does

  1. Stop movement immediately on an accepted interaction.
  2. Face each other — protagonist to character, character to protagonist — before portrait dialogue, unless the event stages it otherwise. Restore authored post-conversation facings after.
  3. Open the conversation for that character's current state — first-time, repeat, mandatory, optional, group, topic menu or quiz.
  4. A character with no available conversation shows no Talk prompt and never opens a blank box.
  5. Inspection: non-portrait dialogue by default; different text per visit and after state changes; first-time and shorter repeat text.
  6. Inspection must not award items, open inventory, or grant unrequested progression.
  7. If an inspection changes state, update visual, prompt, repeat text, objective contribution and collision before control returns.
  8. Repeat interaction must not duplicate objective credit or replay a one-time event.

Gates — a locked thing still answers

  1. Availability may depend on visit, active objective, completed objectives, completed conversations, quiz results, flags and interactable state.
  2. Re-evaluate immediately when any of those change — including while she is standing at the target.
  3. A reachable gated target plays an authored denial line rather than failing silently, and returns to free exploration after.
  4. An invisible wall is never the only explanation. No internal flag names shown to the player.
  5. Repeat denials must not advance objectives. Remove the denial the moment the gate opens.

Doors

  1. Enter on INTERACT when in reach, facing, and the door is accessible. Show Enter; show Leave at an interior exit.
  2. Stop movement and suppress world input; hide the change behind a ~0.2s fade each way.
  3. Place her at the authored spawn, facing in, and apply interior character, interactable, marker and environment state before the fade lifts.
  4. Exit returns to the matching exterior door of the building actually entered — never another student's.
  5. The shared student-house interior retains the exterior house identity for name-board, cast, dialogue and interactables.
  6. Require release after a transition so one press cannot immediately reverse it.
  7. No entry or exit while dialogue, choice, quiz, event or departure is active.

Part 2 — What the code does today

Reading the two halves together

The spine is sound. One press, one resolver, one director. Candidates are rebuilt every frame from live world state, so a character who relocates or an object that changes state is picked up without anything having to be told. The resolver is pure and tested, which is where the fiddly reach-and-facing arithmetic belongs.

The priority ladder is where code and GDD diverge. The spec's first rung — an open UI or a running line of dialogue — is not in the resolver at all; it is handled earlier, by the driver going silent unless the control gate accepts interaction. That is a reasonable place for it, but it means the ladder in the code is four rungs where the document lists five, and nobody reading either one alone would notice.

Every consequence lands in one class. HubVisitDirector is the only place a press turns into anything, which is the right shape — but it is also where the door, the gate check, the denial line, the conversation, the objective report and the departure flag all meet. Worth a closer look once the requirements above are agreed.
