Hub Quest System

Every script in the project that has a hand in tracking a hub visit's objectives, and how a finished conversation actually becomes progress. Read off the code as it stands today.

What a quest is made of

Four authored types. There is no quest script anywhere — a visit is entirely data.

How progress actually happens

Top to bottom: something happens, it is announced, one listener translates it, the machine records it, and everyone else either gets told or asks.

Every script involved

HubVisitDataThe visit asset. Owns the ordered objectives[], plus the cast, the baseline gates and the departure.
HubObjectiveDataOne stage: the line she reads, what finishes it, what changes when it does, who to point a marker at.

HubRuntimeStateThe ledger. Which stage, which targets cleared, what has been said, which gates are open, who has moved.
HubProgressServiceStatic instance holding the visit, the state and the runner. Also answers CanDepart.
HubProgressionListenerThe translator. Turns announcements into Report() calls. The only caller in the project.

HubEventRunnerBoth a producer (raises flags) and a consumer (plays the event an objective asked for).
HubObjectiveController / ViewThe HUD line, the counter and the done cue. The only push consumer of progress.
HubMarkerManagerPolls the active objective every LateUpdate to decide where the markers go.

What holds up

  • One entry point. Report(kind, targetId) is the only way progress is ever credited, and there is exactly one caller.
  • The machine is testable. ObjectiveSequenceRunner and HubRuntimeState are plain C# — no scene, no Unity types in the logic.
  • Genuinely data-driven. Adding a stage is an asset, not a script.
  • The completion order is right. Nothing reports until its trigger has actually finished, so the exchange ends, then the stage completes, then its effects land, then the next line appears.
  • Effects write to state, not the scene. The same list replays identically whether she is standing there or three rooms away.

What does not

  1. One of the five condition kinds cannot fire. HubEventRunner.EventFinished is declared and raised, and nothing anywhere subscribes to it. An objective authored as “wait for event X to finish” would never complete. The only thing that reports EventCompleted is a raised flag that happens to share the name.
  2. A second kind is indistinguishable from it. One FlagRaised is reported twice, as QuizPassed and again as EventCompleted, so at runtime the two are the same thing. Three of the five kinds do real work; two are decoration.
  3. HubRuntimeState is four things. The quest ledger, the dialogue system's IDialogueMemory, the interactables' IProgressionQuery, and the room and return-door bookkeeping — one class, one file, linear list lookups throughout.
  4. The runner both judges and mutates. It decides whether a stage is done and then reaches into the world: opens gates, relocates characters, rewrites conversations, fires events. Deciding and doing are the same object.
  5. Strictly one stage at a time, forever forward. objectiveIndex++, and nothing else. No branching, no side quest, no optional objective, no quest log, and no way to have two things outstanding at once.
  6. The same data is delivered two ways. The HUD is pushed through C# events; the markers poll the runner every LateUpdate for the same facts. Two mechanisms that can disagree by a frame.
  7. Everything is loose string matching. Condition ids, flag ids, gate names and character ids are bare strings compared with IndexOf. A typo fails silently at runtime; HubProblems catches some of it at author time, not all.
  8. Report answers a question nobody asks. It returns a bool saying whether the report counted, and every call site discards it. A report that was rejected — wrong stage, wrong kind, unknown id — leaves no trace anywhere.

The short version

The spine is sound: one entry point, one machine, plain C#, tested, data-driven. This is not the pattern of a system built beside a working one, the way the dialogue stack and the screen fade were.

What is wrong is narrower, and mostly at the edges. Two of the five ways an objective can complete do not work as authored. The state object has collected four unrelated jobs. And the model only describes a straight line of stages — which is fine for Hub 1 as it stands, and will not stretch to a quest log, a side objective, or anything the player can hold two of at once.
