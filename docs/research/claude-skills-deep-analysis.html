Deep Analysis: Story Skills & Claude Code Game Studios

Evidence-grounded read of every skill, agent, rule, hook, and doc in both repos — and what each can and cannot do for Project Astra. Conclusions are mine; the decision is yours.

Compiled 2026-06-21 from full local clones at _reference/Claude-Code-Game-Studios and _reference/story-skills. Where a claim rests on a file, the file is cited. "Not stated" means the file is silent — not that I assumed.

Executive summary

  • Two different categories of tool. Story Skills is a focused 7-skill plugin for a prose-fiction narrative bible with a deterministic continuity engine. Game Studios is a whole process framework — 49 agents, 73 skills, 12 hooks, 11 rules, 41 templates — that imposes a studio org-chart and a 7-phase production pipeline on a Claude Code session.
  • I was wrong earlier, and you were right to push. Game Studios is not "new-game-only." It has an explicit, first-class brownfield / existing-project path (/start → "Existing work" → /project-stage-detect → /adopt → /reverse-document). See the answer.
  • The real catch is structural, not conceptual. Game Studios assumes a generic src/+assets/+design/+production/ layout. Its hooks and rules key off those paths and would silently no-op against Unity's Assets/Scripts/. Its Unity agents are real; its on-disk enforcement is wired for a layout Astra doesn't use.
  • Neither replaces your existing pipeline. Your character-sheets/TEMPLATE.md is richer for a game (FE stats, pancha-bhuta, dharma, visual brief, dialogue library) than anything in either repo. What these add is process discipline (Game Studios) and a continuity engine + relationship/arc tracking (Story Skills).
  • Where this lands: don't adopt either wholesale. Mine Game Studios' creative prompts (art-director, /art-bible, /brainstorm, narrative-director, world-builder, writer); optionally install Story Skills as a parallel lore/continuity bible; and fold the best of both into your own pipeline. Detail in Recommendations.

The core question, answered: can Game Studios run on an existing project?

Yes — it has a designed brownfield path. My earlier "only for new games" claim was incorrect. Verbatim evidence from the files:
  • README.md:158-160 — /start "asks where you are (no idea, vague concept, clear design, existing work)…"
  • .claude/skills/start/SKILL.md:39-44 — option "D) Existing work — I already have design docs, prototypes, code, or significant planning done. I want to organize or continue the work." Path D routes to /project-stage-detect → /adopt.
  • .claude/skills/adopt/SKILL.md:3 — "Brownfield onboarding — audits existing project artifacts for template format compliance… Run this when joining an in-progress project." It refuses fresh projects ("This looks like a fresh project … /adopt is for projects with work to migrate") and never overwrites existing content (:443 "Never regenerate existing artifacts").
  • /reverse-document generates GDD/architecture docs from existing code; a full worked example lives at docs/examples/session-adopt-brownfield.md ("building a game for 3 months before discovering this agent system").
The catch the docs themselves reveal. "Existing project" here means existing design/process artifacts (GDDs, ADRs, stories — possibly in the wrong format) plus code that happens to sit at src/. It does not mean it understands Unity. Specifically:
  • It assumes a generic engine-agnostic tree (src/{gameplay,core,ai,ui}, assets/, design/gdd/, docs/architecture/, production/) — not Assets/Scripts/ + Assets/ScriptableObjects/ + .unity scenes. (.claude/docs/directory-structure.md)
  • Its 12 hooks and 11 path-scoped rules are keyed to those generic paths and silently no-op against a Unity tree — verified by reading every hook. No harm, but no enforcement either, until you rewrite the globs by hand.
  • /adopt greps for design/gdd/*, docs/architecture/adr-*, production/epics/** — it has no Unity awareness; it won't read your scenes or .asset ScriptableObjects.
  • Dropping the template at your repo root would collide with your existing docs/, design/, and a competing CLAUDE.md (theirs is Godot-defaulted/unconfigured here).

Net: attachable in principle, Unity agents present — but on a mature Unity repo its on-disk machinery is inert, so its value to Astra is its agents, skills, templates, and process docs, not its enforcement layer. (Source: dedicated usage-model read of README, CLAUDE.md, UPGRADING.md, all hooks, all rules, workflow-catalog.yaml, start/adopt/project-stage-detect SKILL.md.)

Game Studios — what it actually is

A clone-the-template repo (MIT, v1.0.0, 2026-05-13, solo-maintained, ~22k★, Windows-tested) that turns one Claude Code session into a simulated studio. Its thesis (README.md:25-29): a single chat has no structure — "no one stops you from hardcoding magic numbers, skipping design docs… no QA pass, no design review." It supplies that structure as 49 role-agents, 73 slash-command skills, validation hooks, and path-scoped rules.

Collaborative, not autonomous (CLAUDE.md:35-36, README.md:210): every task follows Question → Options → Decision → Draft → Approval. "Agents MUST ask 'May I write this to [filepath]?' before using Write/Edit." Nothing is committed without your sign-off. It's a scaffold, not a button.

Correction to my first-pass research: the 73 skills are the real product, living in .claude/skills/<name>/SKILL.md. The folder named "CCGS Skill Testing Framework" is an optional, deletable QA test-harness (its files are titled # Skill Test Spec: /art-bible) — CCGS…/README.md: "This folder is self-contained and optional… rm -rf "CCGS Skill Testing Framework" — nothing in .claude/ depends on it." That folder is what misled my earlier count.

The 7-phase lifecycle

From .claude/docs/workflow-catalog.yaml + docs/WORKFLOW-GUIDE.md:

concept → systems-design → technical-setup → pre-production → production → polish → release

Each phase has a /gate-check, but gates are advisory, never hard-blocking ("verdicts are ADVISORY… the user always decides whether to proceed"). The one exception is the vertical-slice gate, which auto-FAILs until a human has playtested. State is file-backed: production/stage.txt (current phase), production/review-mode.txt (full/lean/solo gate intensity), production/session-state/active.md (living checkpoint), and two registries (design/registry/entities.yaml, docs/registry/architecture.yaml) that skills grep to catch cross-document inconsistencies.

How to use it — and how NOT to

Good uses
  • Mine the creative prompts. Read art-director, creative-director, narrative-director, world-builder, writer, game-designer, systems-designer and the /art-bible / /brainstorm / /design-system skill bodies. They're well-structured, theory-grounded prompt scaffolds you can adapt — zero install needed (the clone is already in _reference/).
  • Borrow the artifact standards. The 8-section GDD, the 9-section art bible (esp. §5 Character Design Direction), the asset-spec "visual description + AI-gen prompt" pattern, and the formula-output format are directly reusable in your own docs.
  • As a process checklist. The 7-phase pipeline and gate questions are a sane sanity-check even if you never run the skills.
How NOT to use it
  • Don't clone it as / over your Astra repo root. Folder + CLAUDE.md collisions; inert hooks/rules; a Godot-defaulted config to untangle.
  • Don't expect its hooks/rules to guard your Unity code. They key off src/.../assets/... and never match Assets/Scripts/...; you'd get a false sense of enforcement.
  • Don't lift one skill and expect it to run standalone. Most hard-abort without the concept→art-bible→GDD→architecture artifact chain and the agents they Task-spawn.
  • Don't treat it as a productivity autopilot. It's deliberately collaborative — value is in the structure/questions, and that structure has real overhead for a solo dev on a 60-min prototype.

Fit to Project Astra

Value = the agents, skills, templates, and process docs. The on-disk enforcement is wired for a layout you don't use, and the org-chart/pipeline is heavyweight for a solo 60-minute-prototype scope. The Unity agents are real but generic — they won't know your GameFlow, UnitDefinition SOs, pixel pipeline, or HD-2D identity. Recommended mode: read & adapt, don't adopt. The single most Astra-relevant artifacts are /art-bible §5 (Character Design Direction) and the art-director + narrative-director + world-builder + writer prompts — exactly the gaps a custom Astra character skill would fill.

Story Skills — what it actually is

A focused set of 7 Agent Skills + a deterministic story CLI for planning, tracking, and drafting prose fiction in plain markdown with YAML frontmatter. MIT, v0.3.1, author Daniel Dewhurst, active. Installs as a proper Claude Code plugin:

/plugin marketplace add danjdewhurst/story-skills
/plugin install story-skills@story-skills

The headline feature is the continuity engine: character deaths, promises/payoffs, open questions, scene casts, and durable object/knowledge state live in frontmatter, and story continuity "treats contradictions like a compiler treats type errors" — catching dead characters reappearing, payoffs landing before setup, unfired Chekhov guns, and stale state, deterministically, in CI.

The character & world templates (the actual fields)

character-management — template fields

Frontmatter: name, role (protagonist|antagonist|supporting|minor), age, status (alive|deceased|unknown), died-in (chapter — pairs with deceased so continuity flags posthumous appearances), aliases[], relationships[] ({character, type}), locations[], tags[], arc.

Body sections: Appearance · Personality & Traits · Backstory · Motivations & Goals (external want vs internal need) · Location References · Voice & Speech Patterns (+ 2-3 example dialogue lines) · Character Arc (start / turning points / end) · Timeline (When | Event | Relevance). Relationships are bidirectional with defined inverse pairs (parent↔child, mentor↔student…); family trees live as an indented list in the index.

No game-data fields whatsoever. There is no class, no stats (HP/Str/Skl/Spd/…), no growths, no weapon ranks, no affinity, no recruitment chapter, no sprite/portrait path, no SO reference. This is a novelist's character sheet.

worldbuilding — four templates

  • Location: type, region, population, controlled-by, notable-characters; Description / History / Culture / Notable Features / Current State.
  • System: type (magic/political/tech/religion/economic/military/social/education), prevalence; Overview / Rules & Limitations / History / Practitioners / Impact on Society.
  • Faction: type, status, members, locations; Purpose / Power Base / Members / Conflicts.
  • Artifact: type, status (active|lost|destroyed|hidden|transferred), owner, location; Description / Function (can/can't do, what it costs) / History / Current State.

The import path — and exactly where it stops

There is an import path, but it ingests manuscript prose only:

  • story import draft.md --title "…" (or a directory of chapter files) splits on chapter headings, strips frontmatter, computes word counts, writes chapters/chapter-NN.md, scaffolds the full project, and prints recurring proper-noun candidates as suggestions.
  • It does not parse existing character sheets, lore wikis, faction docs, or stat tables. There's no --characters, no structured-doc importer. Chapter frontmatter (pov, characters, locations, arcs) is left empty.
  • Turning name-candidates into real character/world files is a manual follow-up via story add character / story add location.
For Astra this means your existing .asset units, prototype_design 001.md, and lore docs cannot be auto-imported — only running prose, at chapter granularity. You'd hand-transcribe into the markdown bible.

How to use it — and how NOT to

Good uses (for a game)
  • As a parallel narrative/lore bible for the writing layer — characters' inner lives, motivations (want vs need), arcs, relationships, family trees, factions, mythic artifacts (the relic bow), locations.
  • For its continuity engine — deterministic checks on death ordering, promise→payoff, unfired setups, POV/cast consistency. A strong fit for a story-mode campaign with permadeath (you already have UM-02 Lord Permadeath — exactly the kind of fact story continuity polices).
  • For its plot/arc/foreshadowing structure, including kishōtenketsu — handy for an Indian-myth narrative.
How NOT to use it
  • Don't expect it to replace your character-sheets. It has zero game-data — your TEMPLATE.md is richer for a tactical RPG.
  • Don't expect story import to ingest your Unity SOs or lore docs. It only splits prose manuscripts into chapters.
  • Don't treat a "scene/chapter" as a playable map/encounter. Wrong atomic unit — no map, objectives, turn scripting, or win conditions.
  • Don't run its CLI to generate game content. It's for deterministic maintenance of a markdown prose bible, nothing else.

Fit to Project Astra

Clean to install and genuinely additive for the narrative-bible + continuity layer, which your current pipeline doesn't formalize. But it's silent on everything that makes a unit a game unit (stats, classes, sprites, dialogue assets, map/encounter data), and there's no bridge to your Unity ScriptableObjects. Best role: a parallel prose/lore/continuity bible, hand-synced with the game data — or simply a source of two ideas worth stealing: the continuity-engine concept and the relationship/family-tree registry.
